Lab 01 — eBGP Basics : configuration, vérification et analyse

Parcours : CCNP ENCOR — BGP
Environnement : GNS3, deux routeurs Cisco IOSv et deux VPCS
Statut : Réalisé, vérifié et configurations sauvegardées sur R1 et R2
Objectif : établir une session eBGP entre deux systèmes autonomes, annoncer un réseau LAN de chaque côté et valider la connectivité de bout en bout.

1. Objectifs pédagogiques

À la fin de ce laboratoire, on doit pouvoir :

  • configurer les interfaces d’un routeur Cisco ;
  • comprendre le rôle de no shutdown, description et ip address ;
  • vérifier l’état des interfaces avec show ip interface brief ;
  • configurer une relation eBGP entre deux Autonomous Systems (AS) ;
  • interpréter show ip bgp summary ;
  • annoncer un réseau avec la commande BGP network ;
  • distinguer la table BGP de la table de routage IP ;
  • vérifier la réception des préfixes et leur installation dans la RIB ;
  • tester la connectivité entre deux LAN distants ;
  • sauvegarder la configuration.

3. Configuration de R1 : interfaces

3.1 Commandes réellement exécutées

conf t
hostname R1
do show ip interface brief
interface range g0/0-1
 no shut
exit
interface g0/0
 desc ## Link to R2-G0/0 ##
 ip add 192.168.12.1 255.255.255.252
int g0/1
 desc ## Link to R1-LAN ##
 ip add 192.168.1.1 255.255.255.0
do show ip int brief | exclud un
do wr

3.2 Rôle des commandes

Commande Explication
conf t Entre en mode de configuration globale (configure terminal).
hostname R1 Définit le nom du routeur pour identifier clairement l’équipement dans le terminal.
do show ip interface brief Lance une commande EXEC depuis le mode de configuration. La sortie initiale complète n’a pas été conservée dans le journal récapitulatif.
interface range g0/0-1 Sélectionne simultanément les interfaces GigabitEthernet 0/0 et 0/1.
no shut Active administrativement les interfaces sélectionnées (no shutdown).
exit Quitte le sous-mode d’interface.
interface g0/0 Entre dans la configuration de Gi0/0.
desc ## Link to R2-G0/0 ## Ajoute une description destinée à identifier le lien vers Gi0/0 de R2. La description n’active pas le lien et n’influence pas BGP.
ip add 192.168.12.1 255.255.255.252 Configure l’adresse IPv4 et le masque /30 de la liaison inter-routeurs.
int g0/1 Abréviation de interface GigabitEthernet0/1.
desc ## Link to R1-LAN ## Documente le rôle de l’interface reliée au LAN local de R1.
ip add 192.168.1.1 255.255.255.0 Configure la passerelle du réseau 192.168.1.0/24.
do show ip int brief \| exclud un Affiche un résumé des interfaces et filtre les lignes contenant un. C’est une vérification rapide, mais il faut connaître le filtre utilisé et ne pas le confondre avec une vérification exhaustive.
do wr Sauvegarde la configuration courante dans la configuration de démarrage sur cette plateforme IOS.

Point d’attention observé pendant le TP : une faute de saisie dans le masque (255.255..255.0) a été corrigée immédiatement. Le masque final configuré sur Gi0/1 est bien 255.255.255.0.

3.3 Résultat observé

Les deux interfaces de R1 ont ensuite été observées avec les adresses prévues et l’état up/up :

  • Gi0/0 : 192.168.12.1, liaison vers R2 ;
  • Gi0/1 : 192.168.1.1, liaison vers le LAN 1.

La sortie intégrale ligne par ligne de show ip interface brief n’est pas reproduite ici, car elle n’est pas présente dans le journal disponible. Les adresses et états ci-dessus sont les résultats qui ont été confirmés pendant la séance.

6. Configuration de la session eBGP

6.1 R1 — AS 65001

Commandes réellement exécutées :

enable
configure terminal
router bgp 65001
 neighbor 192.168.12.2 remote-as 65002
end

Explication :

  • enable passe en mode EXEC privilégié ;
  • configure terminal ouvre la configuration globale ;
  • router bgp 65001 active le processus BGP local avec l’AS 65001 ;
  • neighbor 192.168.12.2 remote-as 65002 déclare le voisin BGP à l’adresse 192.168.12.2 et précise que son AS est 65002 ;
  • end quitte le mode de configuration.

6.2 Première vérification sur R1, avant la configuration de R2

Commande : show ip bgp summary

Sortie conservée :

Neighbor        V           AS MsgRcvd MsgSent   TblVer  InQ OutQ Up/Down  State/PfxRcd
192.168.12.2    4        65002       0       0        1    0    0 never    Idle

Interprétation :

  • Neighbor : adresse du voisin configuré ;
  • V 4 : version BGP utilisée, BGP-4 ;
  • AS 65002 : AS distant attendu ;
  • MsgRcvd / MsgSent à 0 : aucun message BGP échangé à ce stade ;
  • Up/Down never : aucune session établie auparavant depuis le démarrage de ce processus ;
  • Idle : la session n’est pas établie.

Pourquoi c’était normal à ce moment-là : R2 n’avait pas encore reçu sa configuration BGP. Un voisin déclaré sur un seul côté ne suffit pas à établir la session.

6.3 R2 — AS 65002

Commandes réellement exécutées :

enable
configure terminal
router bgp 65002
 neighbor 192.168.12.1 remote-as 65001
end

La configuration est symétrique :

  • R2 utilise l’AS local 65002 ;
  • il déclare 192.168.12.1 comme voisin ;
  • il attend l’AS distant 65001.

6.4 Vérification de la session après configuration des deux côtés

Sortie conservée sur R2 :

Neighbor        V           AS MsgRcvd MsgSent   TblVer  InQ OutQ Up/Down  State/PfxRcd
192.168.12.1    4        65001       4       4        1    0    0 00:00:18        0

Sortie conservée sur R1 :

Neighbor        V           AS MsgRcvd MsgSent   TblVer  InQ OutQ Up/Down  State/PfxRcd
192.168.12.2    4        65002       4       4        1    0    0 00:00:40        0

Interprétation :

  • les compteurs MsgRcvd et MsgSent sont désormais non nuls ;
  • Up/Down affiche une durée plutôt que never ;
  • la dernière colonne affiche 0, ce qui signifie que la session est établie mais qu’aucun préfixe n’a encore été reçu de ce voisin ;
  • dans cette sortie, un nombre dans State/PfxRcd représente le nombre de préfixes reçus ; un état comme Idle ou Active indique au contraire que la session n’est pas encore établie.

Conclusion intermédiaire : la session eBGP entre AS 65001 et AS 65002 est établie. La prochaine étape consiste à échanger des routes.

7. Annonce des réseaux LAN avec BGP

7.1 Annonce du LAN de R1

Commandes réellement exécutées :

configure terminal
router bgp 65001
 network 192.168.1.0 mask 255.255.255.0
end

network 192.168.1.0 mask 255.255.255.0 demande à BGP d’annoncer le préfixe 192.168.1.0/24. Sur IOS, la route correspondante doit exister dans la table de routage avec le masque exact pour que l’annonce soit originaire de ce routeur. Ici, le réseau est directement connecté à Gi0/1 de R1.

7.2 Annonce du LAN de R2

Commandes réellement exécutées :

configure terminal
router bgp 65002
 network 192.168.2.0 mask 255.255.255.0
end

R2 annonce de la même manière son réseau connecté 192.168.2.0/24.

À retenir : déclarer un voisin BGP établit la relation de peering ; annoncer un préfixe est une action distincte. Une session peut donc être établie tout en ne transportant aucune route.

8. Vérifier la table BGP et les routes apprises

8.1 Table BGP de R2

Commande : show ip bgp

Sortie exacte conservée :

     Network          Next Hop            Metric LocPrf Weight Path
 *>   192.168.1.0      192.168.12.1             0             0 65001 i
 *>   192.168.2.0      0.0.0.0                  0         32768 i

Interprétation :

  • Network : préfixe connu de BGP ;
  • Next Hop : prochain saut à utiliser pour atteindre le préfixe ;
  • Metric : attribut MED, affiché ici à 0 ;
  • LocPrf : Local Preference, sans valeur affichée dans ces lignes ;
  • Weight : attribut Cisco local au routeur, pas un attribut échangé entre routeurs ;
  • Path : chemin AS et indicateur d’origine ;
  • * : route valide ;
  • > : meilleur chemin sélectionné par BGP ;
  • 192.168.1.0 a pour prochain saut 192.168.12.1 et porte l’AS 65001 dans le chemin : R2 l’a appris de R1 ;
  • 192.168.2.0 a 0.0.0.0 comme prochain saut, ce qui indique que ce préfixe est originaire de R2 lui-même ;
  • 32768 comme Weight pour le préfixe local est la valeur Cisco par défaut couramment attribuée à une route originaire du routeur.

Le i final est le code d’origine BGP : le préfixe a été introduit par une commande network ou une autre méthode d’origine équivalente, plutôt que d’être appris comme route externe EGP historique.

8.2 Routes BGP installées dans la table de routage de R2

Commande : show ip route bgp

Sortie exacte conservée :

B     192.168.1.0/24 [20/0] via 192.168.12.1, 00:01:32

Interprétation :

  • B indique une route apprise par BGP ;
  • 192.168.1.0/24 est le LAN distant de R1 ;
  • [20/0] signifie distance administrative 20 / métrique BGP 0 dans cette entrée ;
  • Distance administrative (AD) = 20 : sur Cisco IOS, la distance administrative sert à départager des routes vers le même préfixe apprises par différentes sources de routage. Plus la valeur est faible, plus la source est préférée. La valeur par défaut d’eBGP est 20; à titre de comparaison, une route OSPF a généralement une AD de 110 et une route RIP de 120. Ainsi, si le même préfixe est disponible via eBGP et OSPF, et qu’aucune autre règle ou particularité ne change la décision, IOS préfère normalement la route eBGP grâce à son AD plus faible. Cette valeur n’est pas l’attribut BGP MED et n’est pas la métrique affichée comme deuxième nombre ;
  • Métrique = 0 : c’est la métrique associée à cette entrée de route BGP dans cette sortie. Ne pas confondre cette valeur avec l’AD 20 ;
  • via 192.168.12.1 désigne le prochain saut ;
  • 00:01:32 est l’âge de la route au moment où la sortie a été capturée.

La route BGP du LAN 1 est donc présente dans la table de routage IP de R2.

8.3 Résumé BGP de R2 après l’annonce

Sortie exacte conservée :

Neighbor        V           AS MsgRcvd MsgSent   TblVer  InQ OutQ Up/Down  State/PfxRcd
192.168.12.1    4        65001       9       9        3    0    0 00:05:13        1

La colonne State/PfxRcd affiche 1 : R2 reçoit maintenant un préfixe de son voisin R1.

8.4 Table BGP de R1

Commande : show ip bgp

Sortie exacte conservée :

     Network          Next Hop            Metric LocPrf Weight Path
 *>   192.168.1.0      0.0.0.0                  0         32768 i
 *>   192.168.2.0      192.168.12.2             0             0 65002 i

Interprétation :

  • 192.168.1.0 est le préfixe local de R1 : prochain saut 0.0.0.0 et Weight 32768 ;
  • 192.168.2.0 est le LAN distant appris de R2 ;
  • son prochain saut est 192.168.12.2 ;
  • le chemin AS contient 65002, ce qui indique que le préfixe a été appris depuis l’AS 65002 ;
  • les marqueurs *> indiquent que les routes sont valides et sélectionnées comme meilleurs chemins.

8.5 Route BGP installée sur R1

Commande : show ip route bgp

Sortie exacte conservée :

B     192.168.2.0/24 [20/0] via 192.168.12.2, 00:01:37

R1 a installé le LAN 2 dans sa table de routage IP via R2.

8.6 Résumé BGP de R1 après l’annonce

Sortie exacte conservée :

Neighbor        V           AS MsgRcvd MsgSent   TblVer  InQ OutQ Up/Down  State/PfxRcd
192.168.12.2    4        65002      10      10        3    0    0 00:06:05        1

La colonne State/PfxRcd vaut 1 : R1 reçoit un préfixe de R2.

Bilan de routage : chaque routeur connaît son LAN local et a appris le LAN distant par eBGP. Les deux routes distantes sont présentes dans les tables de routage IP.

9. Tests de bout en bout

9.1 Depuis R1 vers PC2

Commande et sortie exactes conservées :

R1#ping 192.168.2.10
Sending 5, 100-byte ICMP Echos to 192.168.2.10, timeout is 2 seconds:
!!!!!
Success rate is 100 percent (5/5), round-trip min/avg/max = 1/1/2 ms

Interprétation :

  • R1 envoie cinq requêtes ICMP à 192.168.2.10 ;
  • chaque ! indique une réponse reçue ;
  • 5/5 correspond à 100 % de réussite ;
  • le temps aller-retour minimal/moyen/maximal est de 1/1/2 ms dans ce test.

9.2 Depuis PC2 vers PC1

Commande et sortie exactes conservées :

PC2> ping 192.168.1.10

84 bytes from 192.168.1.10 icmp_seq=1 ttl=62 time=2.046 ms
84 bytes from 192.168.1.10 icmp_seq=2 ttl=62 time=0.953 ms
84 bytes from 192.168.1.10 icmp_seq=3 ttl=62 time=0.993 ms
84 bytes from 192.168.1.10 icmp_seq=4 ttl=62 time=0.886 ms
84 bytes from 192.168.1.10 icmp_seq=5 ttl=62 time=1.049 ms

Interprétation :

  • PC2 joint PC1 à travers les deux routeurs ;
  • les cinq réponses confirment que le trafic passe dans le sens LAN 2 vers LAN 1 ;
  • ttl=62 est le TTL restant dans les réponses reçues ; sa valeur dépend du TTL initial et du nombre de sauts traversés ;
  • les temps rapportés sont les temps aller-retour mesurés par VPCS.

Validation finale : les tests démontrent une connectivité bidirectionnelle entre PC1 et PC2, avec cinq réponses sur cinq dans les deux sens observés.

10. Sauvegarde de la configuration

Les configurations de R1 et R2 ont été sauvegardées après la validation.

Commande de sauvegarde standard à connaître :

copy running-config startup-config

Sur IOS, le routeur peut demander le nom du fichier de destination ; appuyer sur Entrée pour accepter le nom par défaut proposé. Dans cette séance, les sauvegardes ont été confirmées par l’utilisateur. Les sorties textuelles complètes de sauvegarde ne sont pas disponibles dans le journal récapitulatif, donc elles ne sont pas inventées ici.

12. Dépannage : méthode utilisée pour raisonner

Si la session BGP ne monte pas :

  1. vérifier les interfaces avec show ip interface brief ;
  2. vérifier la connectivité IP de la liaison de transit avec ping ;
  3. contrôler les adresses de voisin et les AS distants sous router bgp ;
  4. relire show ip bgp summary et examiner State/PfxRcd ;
  5. une fois la session établie, contrôler l’annonce des préfixes et les routes dans show ip bgp ;
  6. vérifier l’installation des routes avec show ip route bgp ;
  7. tester enfin la connectivité entre les hôtes.

Dans ce TP, le voisin était initialement en état Idle parce que R2 n’avait pas encore été configuré. Après la configuration BGP des deux côtés, la session s’est établie. Ensuite, les annonces network ont permis l’échange des deux préfixes LAN.

Part C — Practical review challenge

Try to answer without looking at the key:

  1. Why could R2 not learn 192.168.1.0/24 before R1 advertised it?
  2. Why do State/PfxRcd = 0 and Idle not mean the same thing?
  3. Which next hop should R1 use to reach 192.168.2.0/24?

Answer key

  1. A BGP session can exchange a prefix only when the prefix is advertised and accepted.
  2. Idle is a BGP session state indicating that the session is not established; 0 in State/PfxRcd means the established neighbor has sent no prefixes.
  3. 192.168.12.2.
  4. show ip route bgp.
  5. PC2 received five ICMP replies from 192.168.1.10.
  6. Cisco IOS normally prefers the route source with the lower administrative distance. The default eBGP AD is 20, lower than OSPF’s usual 110, so eBGP is normally preferred when both provide the same destination and no other relevant condition changes the decision.

If the same prefix is learned through eBGP and OSPF, which source is normally preferred by Cisco IOS based on AD?

eBGP, because its default AD of 20 is lower than OSPF's 110, assuming no other relevant conditions change the decision.

Is administrative distance the same as BGP MED?
